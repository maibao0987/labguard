# 已知限制與後續工作

- 已在此電腦實測 Docker / PostgreSQL 與核心修復流程；主機閘道、kernel 邊界、長時間與併發壓力仍未證明。只有 gateway 加入一般 ingress 網路，其餘實驗與資料服務維持 internal。
- 本機開發模式用 SQLite，沒有容器隔離；只允許單 worker。
- 固定案例檢查不是通用 DAST，沒有任意輸入目標及攻擊鏈。
- XSS 自動檢查只證明儲存後 HTML 未編碼；瀏覽器腳本執行需要另外驗證。
- Session secret 各服務獨立；預設 Cookie 名稱亦依服務區分。Cookie 隔離本身不能取代網路分隔。
- 管理平台只有單一 admin 管理角色，未實作多人協作、MFA、登入限速與密碼輪替介面。
- DB 帳號以初始化方便為優先，尚未拆分 migration owner 與最小權限 runtime role；此為後續硬化項目。
- Alembic baseline 已凍結；尚未有後續升級／降級資料遷移案例。
- 套件有固定版本，尚未加入 hash 驗證、SBOM 或完整依賴弱點稽核；版本固定不保證安全。
- Docker base image 固定 major／發行版標籤，尚未鎖定 digest；需在實際拉取驗證後補上。
- 日誌與報告使用常見憑證字樣遮罩，不保證偵測任意格式敏感資料；禁止放入真實資料。
- 清單與稽核尚未分頁，適合個人小型假資料實驗室。
- 工作上限是程式檢查及網路 timeout，不是可強制殺死任意程式的沙箱；系統沒有任意程式執行功能。
- 沒有提供自動錄影、對外託管、GitHub 遠端推送或通用掃描器整合。

建議後續順序：Docker / PG 併發與主機邊界補驗 → 最小 DB 權限 → 輸入 Schema → 列表分頁 → 本機瀏覽器 E2E CI → 套件與映像供應鏈檢查 → CSRF／路徑穿越／SSRF 進階案例。
